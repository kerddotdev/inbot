# Owner subdomain provisioning

The domain service registers one literal mail subdomain in the configured owner's Cloudflare account. Configure and verify the encrypted transport in Settings > Mail transport or with `PUT /v0/owner/transport` first. Inspect its safe metadata with `GET /v0/owner/transport`; the token is never returned. Clear it with `DELETE /v0/owner/transport` after teardown. Transport changes share the provisioner lock and are refused when clearing would strand recorded infrastructure. Domain UI wiring remains separate work. The REST domain routes are owner-only; agent credentials receive 403 and MCP exposes no domain tools. The CLI and presentational web UI do not yet expose provisioning.

`POST /v0/domains` registers a domain and returns `NOT_STARTED`, planned records, and the incomplete-preview reason. Registration makes no Cloudflare changes. `makeProvisioner().plan(domain)` additionally returns ordered steps and warnings without local or cloud mutation. It uses the routing DNS requirements endpoint and, for an existing sending domain, the sending DNS status endpoint. There is no documented sending DNS preview before creation. New sending DKIM and MX values are unknown and remain empty placeholders until apply; BIND export renders them as comments. Known records are checked through public DNS.

`POST /v0/domains/{domain_id}/apply` executes resumable steps, returning `VERIFYING` after infrastructure setup. `POST .../verify` reruns verification and returns an empty 200 response; retrieve the domain to see the result. `POST .../teardown` removes owned infrastructure and returns `NOT_STARTED`. Delete the domain registration only after its resource ledger is empty. Get, list, update, and `GET .../zone-file` are also available. Feature updates cannot enable tracking, feedback, conflicting providers, or wildcard subdomains. Zone files are BIND text with TXT values split into strings of at most 255 bytes. Errors use `{ name, code, message, fix }`; apex drift across a DNS-affecting step is 409 `action_required`.

## Token permissions

Scope zone permissions to the intended zone and account permissions to the intended account. The names below follow the API permission labels; the dashboard groups them under Zone or Account and presents Read/Edit actions. See the [permission reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/) and the endpoint references below.

| Scope   | Permission                  | Used for                                                               |
| ------- | --------------------------- | ---------------------------------------------------------------------- |
| Zone    | `Zone Zone Read`            | Account-bound zone lookup                                              |
| Zone    | `DNS Write`                 | DNS snapshots, export, exact record deletion                           |
| Zone    | `Zone Settings Write`       | Routing DNS requirements and subdomain enable                          |
| Zone    | `Email Routing Rules Write` | Literal inbox and self-test rules                                      |
| Zone    | `Email Sending: Edit`       | Sending subdomain management and DNS status                            |
| Account | `Email Sending: Edit`       | Synthetic verification send                                            |
| Account | `Workers Scripts Write`     | Worker listing, upload, public URL disable, deletion                   |
| Account | `Workers R2 Storage Write`  | Bucket management and ciphertext buffer access                         |
| Account | `Queues Write`              | Queue management, HTTP pull consumers, pulls/acks, event subscriptions |

The adapter first verifies the token with `GET /accounts/{account_id}/tokens/verify` using the configured account. A 401, 403, or 404 falls back to `GET /user/tokens/verify` for user-issued tokens. No token-type flag is required. Other failures and disabled or expired tokens stop verification without fallback. These endpoints report active/disabled/expired status, not a permission policy. Apply preflights all relevant read access before mutations. Write authorization is checked by Cloudflare on each operation; a 401/403 names the required permission in a `missing_permission` error. An invalid token or wrong resource scope can also cause that response. Inbot does not claim that active-token verification proves all write permissions. The fake explicitly models the full permission set.

## Safety and recovery

- Refuse the zone apex, wildcard names, and domains outside the configured account. Sending creation and routing enable always supply an explicit subdomain name. Rules have one literal `to` matcher; no catch-all operations exist.
- Immediately before each DNS-affecting operation, take and persist a fresh snapshot of apex MX, apex SPF TXT, and `_dmarc.<apex>` records, including IDs, values, priorities, and TTLs. Compare the result with that step's snapshot, then clear it on success. Recover an interrupted step against its persisted pre-step snapshot before proceeding. SOA is outside the protected set. Drift across a step stops further work with `action_required`; restore that step's snapshot before retrying. Owner edits between completed steps do not block apply, verify, or teardown. Inbot does not automatically roll back another actor's apex changes.
- Routing may create `cf2024-1._domainkey.<apex>`. Record its exact ID only when it was absent before Inbot's routing step. It is an expected addition, not permission to modify apex MX/SPF/DMARC.
- Write each creation intent before the provider call and record its resulting ID. Recover interrupted DNS steps from the persisted pre-step snapshot. Lost responses are reconciled by name and scope before retrying. Local mutations are serialized, and mailbox transactions atomically enqueue routing work.
- Previously existing resources are adopted and marked unowned; teardown preserves them. New DNS records are recorded separately by ID, including all records sharing an MX owner name. Apply disables sending previews and Worker public URLs, including on adopted resources.
- Resources are named with the persisted domain UUID. The ledger records the account, zone, parent IDs, ownership, and creation order. It is stored in the encrypted database with the transport token and private age identity. Only the public recipient is sent to the Worker.

Teardown stops inbox rules, checks that the ciphertext bucket is empty, then removes temporary rules, subscription, Worker, consumers, queues, bucket, routing DNS, sending subdomain, and finally its recorded sending DNS IDs. It follows reverse creation order except that the sending subdomain must be deleted before its DNS records: those records are read-only, and Cloudflare removes them with the sending subdomain. Any recorded sending DNS IDs that still exist are then deleted normally.

Before deleting recorded routing DNS IDs, teardown unlocks this subdomain's read-only routing records with `PATCH /zones/{zone_id}/email/routing/dns` and the JSON body `{ "name": "<subdomain>" }`. The name is mandatory in Inbot, and the adapter rejects apex, empty, wildcard, and foreign names. It never sends an unscoped unlock or calls the DELETE routing-disable variant. The unlock, sending subdomain deletion, and every DNS record deletion use the same persisted apex guards.

Interrupted creates are first reconciled read-only. Each successful delete clears its ledger entry; retries preserve progress and repeat unconfirmed operations. HTTP 404 on any recorded resource DELETE (DNS, sending subdomain, rule, subscription, Worker, consumer, queue, or bucket) means already deleted, including DNS removed by sending subdomain deletion. No other delete failure is treated as success. Errors name the failing operation/resource kind without exposing provider bodies, credentials, or record values; error codes and fixes remain stable. Only recorded DNS IDs are explicitly deleted.

The shared routing DKIM is deleted only if Inbot recorded it and no other Cloudflare-routed MX owner remains. Otherwise its ledger entry is retained for a later teardown, so registration deletion remains blocked. An unrecorded shared DKIM is left untouched. Other inboxes, DNS records, buckets, queues, Workers, and subscriptions are never swept by prefix.

Teardown removes inbox routing rules before checking the ciphertext bucket, stopping new inbound mail to those inboxes. A nonempty bucket blocks all remaining resource deletion and retains buffer settings. Re-apply enqueues the existing inboxes so the routing runner recreates their rules. Drain pending mail and review quarantined objects first. Inbot never purges a bucket. A message arriving concurrently can make R2 refuse bucket deletion; remaining ciphertext is retained for reconciliation. Local mail and the inbound private identity survive teardown.

## Verification and routing jobs

Every record is checked with injectable JSON DoH requests to `https://cloudflare-dns.com/dns-query`. Verification compares owner name, type, normalized value, and MX priority, with per-record `MISSING`, `INVALID`, or `VALID` status. Provider routing status and sending acceptance alone cannot verify a domain.

Once DNS is visible, create a temporary literal routing rule for `inbot-selftest@<domain>` targeting the inbound Worker. That address is reserved and cannot be a user inbox. Persist a random 256-bit token and send-attempt timestamp before sending a synthetic message from and to that address with `X-Inbot-Selftest`. Record a separate confirmation timestamp only after Cloudflare confirms the send. Until then, verification reports an attempted send with an unconfirmed outcome, rather than claiming the message was sent. The real buffer puller decrypts the age envelope, parses MIME, and recognizes the exact token, From address, and SMTP recipient. It commits the receipt in the encrypted Store, then deletes the ciphertext and acks the pointer without inserting a mailbox message. Wrong markers do not verify the domain. The same probe may be retried after five minutes if no arrival was observed. A lost send response can produce duplicate synthetic probes; receipt handling is idempotent.

Only observed encrypted-buffer arrival plus valid public DNS changes the status to `VERIFIED`. Remove the temporary rule and invoke the optional `domain.verified` hook. The hook has a durable pending flag and a stable event ID for downstream deduplication after crashes; event stream/webhook delivery remains separate work. Replacing missing infrastructure clears old probe evidence and requires fresh verification.

Inbox creation/deletion inserts or updates `inbox_routing_rules` in the same SQLite transaction. Inbox API responses return immediately. The background runner processes jobs every ten seconds with exponential retry from five seconds to one hour. A five-minute reconcile compares literal rules with current inboxes and repairs missing, disabled, or malformed recorded rules. Lost create responses are adopted by the deterministic rule name and exact matcher/action. Unrelated rules using the same address require owner action. Rule state stays internal; the public inbox resource is unchanged.

Cloudflare event subscriptions need a few minutes to warm up; early delivery events can be missed. Provider-generated delivery events include plaintext subjects and recipient metadata. Inbot sets the events Queue retention to five minutes to limit that exposure. This is a delivery-metadata exception to ciphertext-only inbound storage, and offline periods longer than retention can lose delivery updates. Event subscription readiness is not used to declare inbound verification.

## Worker bundle and release

`pnpm build:worker` uses the root-pinned `esbuild` 0.28.0 to produce one minified ES module at `dist/worker/inbound.js`. `pnpm build` includes this step. Upload is multipart with `main_module: inbound.js`, R2/Queue bindings, and public `RECIPIENT`; a separate script-subdomain call disables both workers.dev and preview URLs.

Release packaging must ship `dist/worker/inbound.js` beside the compiled server tree, preserving `dist/apps/server/src/provision/provisioner.js` and its relative path to the bundle. Provisioning reads the file at apply time and reports an actionable error if it is missing. No Wrangler deployment or real-account provisioning is part of build/test.

The Worker imports envelope crypto, frame validation, and key generation without the service's Effect schemas. Service-side schemas remain available. With the same esbuild version and settings, the measured baseline was 387,089 bytes and the resulting bundle is 138,290 bytes (64.3% smaller). The build and bundle test reject Effect inputs and enforce a 150 KB bound.

Migration 9 adds domains, resource ownership/progress, self-test send confirmation, and inbox routing jobs after owner-session migration 8. The strict contiguous migration runner remains unchanged, with migrations 1 through 9.
